## Next code deploy: check the forwarded headers

Commits after `a43aeff` change who the app believes `X-Forwarded-For` from. After the next
`git pull && docker compose up -d --build`:

```bash
docker compose logs chatbot | grep 'believed only from'
#   Expect a Docker gateway such as 172.18.0.1. 127.0.0.1 means no default route was found.
docker compose exec chatbot sh -c 'tail -n +2 /proc/net/route'
#   The row with Destination 00000000 is where that came from.
docker compose logs --tail 200 chatbot | grep 'GET /health/ready' | grep -v 127.0.0.1 | tail -5
#   After a request from outside, the line shows that caller's public address.
```

If outside requests show the gateway instead, nginx is not sending `X-Forwarded-For`. If they
show a public address that is not the caller's, stop and report it. Neither affects replies.
Then, from outside: `curl -s -H 'X-Forwarded-For: 127.0.0.1' https://bot.minghwee.com/health/ready`
must show no `warnings`.

The same deploy carries the suggest parser fix. To see whether the bot ever hit that error, run
this BEFORE deploying, because `up -d --build` deletes the old container's log:

```bash
docker compose logs chatbot | grep -c 'JSON-mode response was unparseable'
docker compose logs chatbot | grep -c 'suggest: model output was not JSON'
```

Replaced-thread recording ships switched off, with its SQL not applied. Nothing to do for it.

## What this deploy changes

- The bot refuses to start without Postgres, where it used to fall back to memory.
- The container's health label comes from `/health/ready`: database, Whapi token, live Whapi
  channel and checkpointer.
- A stop or deploy answers waiting messages, up to 45s.
- `warnings` leaves the public health body.

The startup scan stays off and no SQL is applied. Checkpoint pruning and `client_notes` are not
built.

## Stage 3: Deploy

```bash
git pull
git log -1 --oneline                   # the commit you pushed
docker compose up -d --build
```

**This one restart is not protected.** The old code is what stops, and it drops messages waiting
in its buffer. From the next restart on, they are answered.

If the database cannot be reached, the new code retries for 60s, exits, and Docker keeps
restarting it. That is intended, but the bot sends nothing meanwhile.

## Stage 5: nginx allowlist

Today nginx forwards every path. `docs/nginx_allowlist.conf` replaces that. **It has not been
parsed by nginx, and the server's config has not been read**, so look before you change anything.

```bash
sudo nginx -T > ~/nginx_before_$(date +%Y%m%d_%H%M%S).txt 2>&1
sudo nginx -T 2>/dev/null | grep -nE 'server_name|listen|location|proxy_pass'
```

Stop and ask if the bot's server block has any `location` not in the allowlist. Something may
depend on it. Otherwise:

1. Copy the server block's file to your home folder as a backup.
2. Put the two `limit_req_zone` lines in `/etc/nginx/conf.d/bot_limits.conf`.
3. Replace the catch-all `location /` in the HTTPS block with the blocks from the file. Keep the
   server's own `/kb-render/` block if it differs. Leave the port 80 block alone.
4. Apply it:

```bash
sudo nginx -t && sudo systemctl reload nginx
```

## Stage 7: Uptime monitor

Set it up only after stage 3. Until then the live check does not exist.

| Setting | Value |
|---|---|
| URL | `https://bot.minghwee.com/health/ready` |
| Method | GET |
| Check type | Keyword must be present |
| Keyword | `"status":"ok"` with the quotes and no space |
| Interval | 1 minute or longer |
| Timeout | 10 seconds |
| Alert after | 2 failures in a row |

Always test on the body: this URL answers 200 even when degraded. To prove the alert reaches
someone, change the keyword to a wrong value for one check, then change it back.

A Whapi outage now alerts too, as decided. If `whapi_channel` is false, look at the channel in
the Whapi dashboard first.
